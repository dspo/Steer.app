# 产品 / 架构 / 技术问题清单

> 三份架构文档（engine / ui / domain-model）之外的待决问题，集中在此。每条附机制背景、选项与建议；**回答后把结论并入对应文档的决策记录表，本条随之删除**。编号接续三份文档已裁决的 Q1–Q6。

## Q7：用户的 pi 登录态（credentials）要不要从系统 `~/.pi` 导入？

**背景（机制）**：引擎架构决定把 pi 的状态与配置**完全隔离**到 `<appData>/pi/`（engine spike ③），不渗用户的 `~/.pi`。但 pi 的**provider 登录凭据**（API key / OAuth）存在其配置目录里——目录一隔离，用户之前在终端里 `pi` 登录过的所有 provider，在我们的 app 里都是未登录状态，第一次用要重新登录一遍。用户如果用多个 provider（Anthropic / OpenAI / GLM / …），重新登录的摩擦会被放大。

**选项**：
- **A 完全隔离**：不碰 `~/.pi`，用户在我们的设置页逐个重新登录。最干净（无跨目录读、无版本漂移风险），代价是首次体验差。
- **B 一次性导入向导**：首次启动检测 `~/.pi` 的凭据文件，弹「导入系统 pi 登录态」向导，**复制**（非引用）到我们的目录；此后两边各自独立、互不回写。首次体验好，长期仍然完全隔离。
- **C 双向共享**：直接指向 `~/.pi` 读凭据。省事，但配置目录隔离被开洞，pi 升级改凭据格式时我们被动受损。

**建议**：B（复制导入，一次性；隔离承诺不破，摩擦只发生在第一次）。

**需要你回答**：A / B / C？

## Q8：产品名与应用身份

**背景**：仓库当前 manifest 是 `name: "Pi"`、`id: "dev.dspo.pi"`、窗口标题 "Pi"、UI 里 logo 画的是 π。产品若要长成独立应用（而非内部原型），名字与身份要定：① 应用名（叫 **Pi** 会与 pi CLI 本身同名——搜索、口头交流都会歧义；Steer 对 manox 的处理是另起品牌名）；② bundle id（`dev.dspo.pi` 是否保留）；③ 品牌色（当前主题 primary 是紫 #8b7cf6，是否就是品牌色）。

**选项**：
- **A 沿用 Pi**：与 CLI 同名，强调「就是 pi 的官方桌面」定位（如果我们与 pi 上游有这层关系）。
- **B 另起品牌名**（如 Steer↔manox 的先例），pi 只是引擎。名字此刻随意占位，后续可换——代码里名字集中在一处（nsh.json + 常量）。
- **C 先不定**：内部阶段继续叫 Pi，发布前再定（激进纪律允许改名不留兼容）。

**建议**：C 先不定，但把**命名集中在 nsh.json 与单一常量文件**，避免名字散进代码深处。

**需要你回答**：A / B / C？若 B，有没有候选名？

## Q9：界面语言策略

**背景**：Steer 的 i18n 纪律是**中文第一语言**（Fluent，zh-CN primary + en fallback），全部 UI 文案走键值。nsh 侧有 `nsh-i18n` 模块与 `set_locale` 能力，但其实际形态未验证（可并入 spike）。当前 nsh-pi 的 mock 文案是中英混排（「终端」「Pi Session」「拖页签换 panel…」）。

**选项**：
- **A 对齐 Steer：zh-CN 第一 + en fallback**，从 v1 就走键值表（nsh-i18n 或自带轻量 Fluent）。成本：所有文案进键表 + parity 测试；收益：与你的产品习惯一致，避免后期全量回捞硬编码文案。
- **B v1 英文单语**，i18n 挂 v2。最快，但硬编码文案会累积，后期回捞是一次性重税。
- **C 中文单语**（不做键表，直接写中文）。最省，但永久放弃英文。

**建议**：A（键表从第一天立住，初始只填 zh-CN，en 留空 fallback）——键表纪律越晚立越贵。

**需要你回答**：A / B / C？

## Q10：要不要给原生 pi CLI 留一条「互通」的桥？

**背景**：Q1 裁决后，我们的会话文件住进 `<appData>/pi/containers/` 的自定义布局，系统的 pi CLI 看不到它们。但 pi CLI 支持 `--session <文件路径>` 直开某个会话文件——也就是说「在终端里用原生 pi 接续我们管理的某个会话」在机制上几乎免费：菜单项 → spawn 一个终端容器 → `pi --session <captain 文件路径>`。

**选项**：
- **A 不互通**：我们的会话只在我们的 UI 存在。最纯粹的隔离，没有边界问题。
- **B 单向桥接**：会话/容器行菜单提供「在终端用 pi 打开」（只读意图上也不强制——pi 会照常写该文件，两边的写入竞争由 pi 自己的文件锁语义兜底）。对重度用户是高价值逃生舱，成本低（一个菜单项 + 一条 argv）。
- **C 双向**：还支持把系统 pi 的既有会话**导入**我们的目录（复制文件 + 注册表登记）。导入本身不难，但引入「外部文件格式校验/版本差异」面。

**建议**：B（只做出口，不做入口；C 等真实需求）。

**需要你回答**：A / B / C？

## Q11：归档（archived）容器在哪里可见、如何恢复？

**背景**：容器 archive 后从侧栏摘行（domain-model §4.2），但「永久在册、unarchive 整树复活」意味着必须有一个可见的恢复入口，否则归档等于事实删除。Steer 侧这个问题同样挂账（「归档分区面落地即销账」），说明它不好做但要早定方向。

**选项**：
- **A 侧栏过滤开关**：侧栏顶部一个 All / Active / Archived 三态过滤，归档行淡显在原分组位置。信息密度差（归档多了会淹侧栏）。
- **B 项目内折叠分区**：每个项目组下「已归档」折叠区（ThinkRail Settled shelf 同思路），归档容器按 settle 时间排。与 shelf 语义天然合并。
- **C 独立管理页**：设置或命令面板里的归档浏览页（搜索/批量恢复）。功能全但入口深。

**建议**：B（与 Settled shelf 是同一个投影面——settled 与 archived 本就是容器的两种静默态，一个分区承载）。

**需要你回答**：A / B / C？

## Q12：托盘、系统通知、后台完成的提醒——v1 的取舍

**背景**：nsh 原生提供 `Tray`（托盘图标 + 菜单）、`Notifications`（系统通知，含权限申请）、`GlobalShortcut`。这个产品的核心循环是「给 agent 派活 → agent 在后台跑 → 回来看结果」——**后台完成提醒**是这个循环的关键一环：切到别的容器/别的应用时，captain 跑完了你不知道。Steer 有托盘常驻。

**选项**：
- **A v1 全不要**：单窗口、关窗即退，通知等 v2。
- **B 只做系统通知**：turn settle / 子会话交付时发系统通知（可设置关）；不做托盘，窗口关闭即引擎随进程退出。最小成本拿到核心循环的闭环。
- **C 托盘 + 通知**：托盘常驻（关窗不退出，engine 继续跑后台任务）——意味着引入「应用生命周期 ≠ 窗口生命周期」的全套语义（退出菜单、单实例、后台 run 的电源管理）。

**建议**：B（通知是核心体验，托盘是生命週期承诺，后者牵动 engine 常驻语义，v2 再议）。

**需要你回答**：A / B / C？

## Q13：子代理「定义」体系的来源

**背景**：调度工具 `dispatch` 的形状是 `spawn = <定义名>`（Steer D13 同款）——定义携带 persona（提示词取向）、工具过滤、模型、权限天花板。问题：这些**定义从哪来**？

**选项**：
- **A 代码即配置**：定义硬编码在 engine 内置扩展里（内置 2-3 个：general / reviewer / researcher）。零管理面，用户不可定制。
- **B 用户定义文件**：`<appData>/agents/*.toml`（或 json）+ 设置页列表管理；engine 启动扫描，内置定义作为兜底。格式自定，量小（一个定义十来行）。
- **C 复用 pi 的 skill 生态**：pi 已有 skill 文件发现机制；把 skill 映射为子代理 persona（skill 的指令 = persona 提示词）。复用上游生态，但语义映射（工具过滤/权限）未必齐。

**建议**：B（内置 + 用户文件；C 作为后续兼容层研究——pi 的 skill 生态是真实存在的人才库，值得在 v2 摸清映射）。

**需要你回答**：A / B / C？（若 B，文件格式 toml/json 有偏好吗？）

## Q14：自更新渠道

**背景**：引擎架构定了「pi 版本随 app 走、经应用更新分发」——意味着应用需要一个自更新通道（nsh/updater 原语：check → download 进度 → installAndRestart，源配 GitHub Releases 或任意 host）。Steer 的通道是 GitHub Releases（tag 触发三路构建，dmg/deb/rpm）。

**选项**：
- **A GitHub Releases**：与 Steer 同款，nsh updater 原生支持该源。前提：仓库公开或配 token。
- **B v1 不做自更新**：手动分发 dmg，更新靠重新下载。省掉发布管线，但「自管 pi 版本」的价值兑现方式变成「重新下载新 dmg」。
- **C 自建更新源**（对象存储 + manifest）：渠道自主可控，多一套基础设施。

**建议**：A（若仓库公开）；B 仅在仓库暂不可公开时作为过渡。

**需要你回答**：A / B / C？仓库是否公开？

## Q15：外部容器的种类边界

**背景**：容器 kind 里 external 臂当前列出 Terminal / Claude / Codex / Copilot（对齐 Steer）。Steer 侧还有两类**GUI 注入式直发**不进容器 API：VS Code（打开目录）与 ChatGPT.app（URL scheme 唤起）。它们不算容器（无 PTY、无转录），只是快捷动作。

**选项**：
- **A v1 只做四类**（Terminal / Claude / Codex / Copilot TUI），VS Code / ChatGPT 直发挂账——聚焦容器模型，快捷动作等侧栏组菜单阶段（v3）再评估。
- **B v1 就带直发**：Launcher 动作行加 VS Code / ChatGPT 两个图标（纯 `openUrl`/spawn，无容器语义）。成本极低（各一行），但会诱惑「把非容器动作塞进容器语义」的边界模糊。

**建议**：A（边界干净优先；直发动作与容器无关，晚做无技术债）。

**需要你回答**：A / B？
