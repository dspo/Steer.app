## 待讨论

### Q10（重开）：Zu 增强写入 captain 会话文件的边界

**为什么重开**：第三轮你明确了两点，Q10 的问题形态变了——① Q1 恢复路径即关系，subagents 隔离（pi 看不见，已无争议）；② **Pi → Zu 兼容是硬约束**，Pi → Zu 的读取方向不需要再讨论。剩下真正未定的是**反方向的写入面**：Zu 自己的动作要不要、以什么形式写进 **pi 可见的 captain 会话文件**。

**背景（机制）**：captain 会话文件住 pi 原生存储，pi CLI 能打开它、回放它。Zu 的某些动作天然会产生「对话之外的事件」——比如 Captain 派发子代理（`dispatch`）、运行中引导（`inject`）、子代理交付（`delivered`）。这些事件在 Steer 里是 journal 的 `run/*` 行 + 转录里的 note 行（「Captain 引导 run X」）。

现在有三个选择，差异在于 **pi CLI 回放该会话时看到什么**：

- **A 不写入**：Zu 的调度事件只进 `zu/registry.json` 与我们自己的 UI 投影，captain 会话文件里只有用户消息和模型回复。pi CLI 打开时干净如常——代价是「这个会话派过哪些子代理」在 pi 侧完全不可见，历史只剩结果。
- **B 写成普通消息条目**：调度事件作为一条 system/user 类消息插入 captain 会话（pi CLI 回放时能看到「派发 reviewer 子代理」这类行）。可见性好，但污染了模型上下文（下次续跑时这些注入会进 prompt），需要 pi 支持不参与上下文的条目类型——若支持则可控，不支持则不可取。
- **C 写成自定义条目类型**（若 pi 会话格式支持）：pi CLI 回放时可能忽略或显示为未知行，Zu 侧完整解析。这是最理想的形态，但完全取决于 spike ③② 的实测结果（pi 是否容忍未知条目、`SessionManager` 是否提供写入 API）。

**建议**：**先跑 spike ③②，按实测结果定**——支持自定义条目 → C；不支持但支持「不参与上下文的条目」→ B 的变体；两者都不行 → A（并在名册 UI 里承担全部历史可见性）。

**需要你回答**：等 spike 结果再定，还是现在就指定优先级偏好（例如「宁可 pi 侧不可见，也要保证模型上下文干净」= A 优先）？

### Q19：子代理定义的「项目来源」目录放哪？（Q13 的落地细节）

**背景**：Q13 定了三来源 builtin / personal / project。前两者位置明确（代码内置；`~/.pi/zu/agents/`）。**project 来源**——即「跟着仓库走、可提交进 git 的子代理定义」——放哪没有定：

- **A `.pi/agents/`（仓库根）**：与 pi 的既有约定对齐（pi 的资源发现约定），能被 pi CLI 也看到（虽然 pi 不认识子代理语义，但至少文件在熟悉的位置）。
- **B `.zu/agents/`（仓库根）**：Zu 专属，不冒充 pi 的命名空间；但用户会问「为什么不是 `.pi`」。
- **C 复用现有目录约定（如 `.claude/agents/`）**：与 Claude Code 生态互通（定义文件格式本来就同款），迁移成本最低；但把 Zu 绑到了第三方约定。

**建议**：A（`.pi/agents/`）——「Zu 是 pi 的 desktop 端」的定位下，资源就该放 pi 的约定位置；pi 不认识语义是我们的增强，不影响文件位置的一致性。

**需要你回答**：A / B / C？

### Q20：多窗口的打开面（Q2 的配套）

**背景**：Q2 定了「单容器画布 + 跨容器需求走多窗口」。但**什么时候开新窗口**没有定：

- **A 不主动开**：只有用户显式动作（⌘⇧N / 命令面板「在新窗口打开」/ 拖侧栏行到 Dock 外部）才开新窗口。每次窗口 = 一个容器，各自独立。
- **B 按项目自动分窗**：打开另一个项目的容器时自动新开窗口。少一步操作，但窗口数量会失控（用户可能只是想看一眼）。
- **C v1 完全不做多窗口**：单窗口，跨容器切换靠侧栏。最简单，跨容器并看的需求先不满足（用户抱怨了再做）。

**建议**：C（v1 不做），因为多窗口会带来「哪个窗口拥有托盘图标」「关掉一个窗口是否退出应用」「布局 stash 按容器还是按窗口」等一连串语义，价值却是低频的。真要做时按 A。

**需要你回答**：A / B / C？

### Q21：Zoom（单 panel 最大化）的持久性

**背景**：DockArea 有 `toggleZoom`——一个 panel 铺满整个画布。问题是：**zoom 状态要不要进布局 stash**？即你 zoom 了某个 panel、切到另一个容器再切回来，应该还是 zoom 的，还是恢复成未 zoom？

- **A 不持久**（当前实现）：zoom 是当前会话的临时动作，切走即还原。符合「zoom 是看细节的临时手段」直觉。
- **B 持久**：写进 stash，切回来还是 zoom。适合「我固定用一个 panel 工作」的用户，但也可能让用户困惑（切回来发现只剩一个 panel，以为布局丢了）。

**建议**：A（不持久，现实现即如此），并在状态条保留「已放大」指示让用户随时知道。

**需要你回答**：A / B？

### Q22：turn 进行中切换容器 / 关窗的行为

**背景**：后台 run 继续是托盘常驻的前提（Q12/Q16）。但有两个边界：

1. **切容器**：容器 A 的 turn 正在跑，用户切到容器 B。A 的 run 应该继续（这是后台语义），回 A 时接上流式。**但**：A 的 sheet 被 stash 后，它的流式事件还推给 UI 吗（只是不渲染），还是 engine 侧缓冲等 restore？（内存与实时性的取舍）
2. **关窗**：关窗 = 收起（Q16），run 继续。**但**用户点「退出」时：① 有活跃 run → 立即中断并退出 / ② 提示确认 / ③ 拒绝退出直到 run 结束？Q16 说关窗无确认，但**退出**是另一回事（会杀 engine）。

**建议**：1 = engine 继续推、UI 只对当前容器渲染（其余丢弃增量，restore 时从转录重建——成本极低，避免缓冲管理）；2 = 有活跃 run 时退出弹确认（列出几个在跑）。

**需要你回答**：1 同意丢弃增量重建吗？2 退出确认还是静默中断？
